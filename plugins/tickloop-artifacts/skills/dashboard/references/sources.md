# Where the numbers come from

## What can be live

Data that changes is a live query, so the page stays current and readers can check each number. Rows a connector gave you are a live query too, unless the person asked for a fixed copy, and then you don't offer a live one. A file of them shows every reader what you read with your own access.

What one query can't do, several datasets can, joined in a `dash.calc`. Before one call uses another's answer, read [dependent-calls](dependent-calls.md). An answer too big for the dashboard is refused, so aggregate at the connector. Your own arithmetic can go in the query or a calc. A sender, date, label or status is data. Three things can't be live: your own reading of text, such as sorting, scoring or summing it up; answers from a tool only your session has; and a tool its connector doesn't mark read-only, which no dashboard calls. For those, attach a file of the rows and tell the person why the numbers won't update. If readers may lack a connector's access, say so and let the person choose. If what you hand over isn't live, tell the person and why, since nothing else will.

A connector that needs a sign-in or isn't connected shows no tools, like one that isn't there. Going on without it is their choice, so ask before you use other data. Say why in terms of what they asked for: "Your deals are in HubSpot, which needs a sign-in before I can read them." Customize › Connectors, which the + menu in the message box leads to, is where they connect it. When they say it is done, make the call again. One table refused says nothing of the rest of its connector: name it, and who could grant access to it.

When more queries wait than a connector runs at once (four), `data-fetchpriority`, as in HTML, on a mark or around it, says which go first: `"high"` on the few numbers a reader looks at first, `"low"` on a large detail table. With room for everything it does nothing.

## A loader

`dash.loader(id, {description, fn})` turns an answer that isn't rows into rows. Only rows can be marked by cell, previewed or downloaded. In `runs`, an `ok` with `rows: 0` and `value: true` loaded something else. On every load the page makes the dataset's call, then runs `fn({answer, call, args, read})`. `answer` is the tool's answer: its structured content when it has one, else its content, each text parsed if it is JSON, out of a wrapper whose only key is `result`, and a list for several items. For an attached file it is the text, or a JSON file's value. `args` are the call's args, with filters filled in. Return row objects, `{columns, rows, cut}` or `{data, columns, cut, meta}`, where `cut: true` means the rows are incomplete. `{data}` alone is a record.

Base it on your own call's answer, or on the file you attached. An answer can also come back failed inside a success, still running, or cut short. An `error` key, as text or `{message}`, fails the load by itself. To fail the source, throw an `Error` with the connector's words, since an empty result would read as a true zero. Type cells by the connector's column types: an amount is a number, while "02139" and an id above 2^53, which would lose digits, stay text. Readers see the loader's code, and it reruns when that changes, so it uses nothing from outside itself.

`read` has parsers: `read.bigquery(answer)` for BigQuery JSON, `read.governed(answer)` for a `<query_result>` XML, `read.snowflake(answer)` for a `result_set`, `read.databricks(answer)` for a statement. Each returns a promise of `{data, columns, cut, meta}`: return it, or `await` it before you read or change what it gives. A failure the answer reports is thrown in the connector's own words, and so is a query still running. Where the answer reports more rows than it holds, `cut` is true. The rows may be under a key the parser missed or behind a further call, so read them yourself. If the loader still returns none, the source fails. Snowflake and Databricks cells come typed. But dates and whole numbers of 2^53 or more stay text, and a long decimal rounds. A NULL in a Snowflake text column is `""`.

`meta` is what the answer says about its rows: return whatever it has that a reader would check a number against, such as the query that really ran or the run's address, as `[{label, value, type?: "code", lang?}]`, label and value both text, or the entry is dropped. Readers check numbers against it, so it contains only what the answer carried.

`call(tool, args)` makes another call on the same connector, as the reader, for a next page or a running query; a load makes at most 30. Its tool must be one a dataset of this dashboard calls on that connector, since those are the tools the reader allowed; while the connector is shared, one of the shared calls' tools. So a tool only a loader calls needs a dataset of its own. A loader that pages does so on every load, for every reader, so it asks for what the page shows and no more, and returns `cut: true` where it stops short. A share never answers a dataset a loader reads: on a shared connector its whole load runs with each viewer's own access. Tell the person that this query needs each viewer's own access. `call(tool, args, {poll: true})` waits a second first, for a query left running.

## A connector someone shares

Nobody shares anything on a new dashboard. A share is one editor's approval of exact calls on one connector, made in Sources: a connector's Viewers use, Their access or Your access. Picking Your access first lists each call that will run with their access and what each filter may hold, and shares only once they confirm. Each new one replaces the last. Then the dashboard runs those calls, and only those, with that person's access for everyone who opens the dashboard, and keeps the results in the dashboard, where anyone who can open it may read them. Ending the share deletes them. A call is its `source` as stored: `{tool, args, rules?}` with each `{{name}}` left in. A query whose blanks a rule doesn't fully pin, or that a loader reads, isn't shared: it runs as each viewer. So if a query was added since the share, or changed by one character, readers see "Shared results are updating." until it is approved again; an editor who saves one in Sources is asked to. A share also ends, and its results go, when the sharer's connector is disconnected, turned off, removed or replaced by another of that name, or when they can no longer edit the dashboard.

`dash/settings` records whose account each connector runs on, in `shared: {<connector>: {id, name, at}}`. The dashboard writes it when someone shares; you never do. A connector not named there runs as each viewer. Read that document before you change or add a query. A change that leaves every `source` alone needs none of this.

You can't share or end a share from a chat; only the person can, in Sources. You can't read what a shared query showed readers either: to see its numbers, run it on the person's own connector if it only reads, and say whose access gave them. When you change a query on a shared connector, tell the person what readers will see ("Shared results are updating.") until the sharer, or another editor picking Your access, approves it again in Sources.

A rule limits what any viewer can run as the sharer, and the sharer sees it only when they approve. So on someone else's share, a rule isn't yours to loosen or drop, even when they ask: say whose share it is and that the change is theirs to make. A stricter one is fine on anyone's share. Like any change, it binds nobody until it is shared again, so say so.

`updates` in `dash/settings` is how old a shared result may be when someone opens the page, as `viewed`, `5min`, `hour`, `day`, `week` or a number of minutes, never under 5 minutes; any other word means `viewed`. If the person says how fresh it must be, `update` it with a number.

## Files, and older forms

A file is a copy, whatever it was copied from: a newer one shows only when someone uploads it. `schedule` says in words how a file stays current. Past `staleAfterHours`, about twice the time between updates, the file shows as stale.

**Made live.** They asked, so do it even if the data looks fixed. If it can't be live, say why and name the connector that would hold it. Don't offer another upload or sample rows then: they don't answer that request. The page reads the file's column names, so compare the answer's columns with the file's: the query gives those names, or a loader added to the page does, and nothing else on the page changes. Run it beside the file and tell the person where figures for the same period disagree. `set` the whole document under the same id, with a title and description true of the query and without `updated` and `fixed`. Using `update` would merge the two sources. Leave the file attached, as it may be their only copy, and tell them it still is. Keep its `url` as `formerFile`, a field only you read, since nothing else names the file now.

**Kept current.** Upload the newer file and `set` the whole document under the same id, with its new `url` and `updated`. The page reads the file's column names, so compare the new file's columns with the old one's.

**Removed**, when the person asks (Sources calls one nothing uses Unused): only an editor or you can remove a source. First change any page file that names its id, then delete its document. Its attached file stays with the dashboard, readable by everyone who can open it: tell the person.

An old `kind: "rows"` source shows "Didn't load": attach its rows as a JSON file. `kind: "query"` is an older form the dashboard doesn't run: when you change it, rewrite it as `"call"`, with its own quoting and rules, and a loader unless its answer is plain rows.

## What readers see in Sources

Each source's title and description, then, folded, Query (each argument, with each filter's value now, and the connector and tool), Transform (the loader's code) and Result (its rows, with the number they clicked lit, and `meta`). A source that waits on the reader says on what: permission to use the connector's tools (Allow), a connector turned off in Customize (Turn on), a sign-in (Reconnect), a connector they don't have (Connect), or, for someone without an account, signing in (Sign in). One whose refresh failed keeps its last rows, marked. An editor also gets Edit query: Name, Description and each argument; Test runs the page with it unsaved, and Save writes the source back with `edit: {via: "user", at}`. A file has File (its first rows, its size, when it was uploaded, and Download), and an editor Edit file: they change or replace its text, Test runs the page with it unsaved, and Save attaches it as a new file and `set`s the source with its new `url`, `name`, `updated: {at, by}` and `edit: {via: "user", at}`. A calculation has Formula (its inputs and code) and Result. Below the sources, each connector the queries use, with whose access it runs.
